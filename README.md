# DataSkewAnalysis

Сравнительный анализ 7 методов решения проблемы перекоса данных (data skew) при выполнении join-операций в Apache Spark.

## Стек технологий

- Java 17
- Apache Spark 3.5.0 (Scala 2.12)
- Maven
- Docker Compose (кластер: 1 master + 3 worker)

## Сборка и запуск

```bash
# Сборка
mvn clean package

# Поднять кластер (master + 3 worker × 2 cores × 2 GB)
docker-compose up -d

# Запуск одного бенчмарка на кластере
docker exec spark-master /opt/spark/bin/spark-submit \
  --master spark://spark-master:7077 \
  --driver-memory 1g \
  --executor-memory 1g \
  --executor-cores 2 \
  --total-executor-cores 6 \
  --class com.vanmors.dataskew.AQE.AQEBenchmark \
  /opt/spark-apps/DataSkewAnalysis-1.0-SNAPSHOT.jar

# Остановить кластер
docker-compose down
```

## Реализованные методы

| # | Метод | Класс | Описание |
|---|---|---|---|
| 1 | Adaptive Query Execution | `AQE.AQEBenchmark` | Встроенная оптимизация Spark: автоматическое разбиение скошенных партиций при join. Настраивается через `spark.sql.adaptive.*` |
| 2 | Salting | `salting.SaltingBenchmark` | Добавление случайной соли к ключу join в большой таблице и размножение малой таблицы по всем значениям соли. Распределяет горячий ключ по нескольким партициям |
| 3 | Broadcast Join | `broadcast.BroadcastJoinBenchmark` | Рассылка малой таблицы на все исполнители через `broadcast()`. Join выполняется локально без shuffle |
| 4 | Pre-aggregation | `preaggregation.PreAggregationBenchmark` | Предварительная агрегация (`groupBy` + `agg`) большой таблицы по ключу join перед выполнением join. Сокращает объём скошенных данных |
| 5 | Map-side Join (Co-partitioned) | `MapSideJoin.MapSideJoinBenchmark` | Обе таблицы заранее со-разбиваются по ключу join через `repartition()` + кэширование. Join выполняется без дополнительного shuffle |
| 6 | PRPQ | `PRPQ.PRPQBenchmark` | Partial Redistribution & Partial Query (Cheng et al., 2014). Тяжёлые ключи обрабатываются через broadcast join, остальные — через обычный shuffle join, результаты объединяются через union |
| 7 | Patch-based Repartitioning | `PatchBasedRepartitioning.PatchBasedBenchmark` | На основе работы Kassela E. (2023–2025). Скошенные ключи разбиваются на патчи фиксированного размера, малая таблица реплицируется только для скошенных ключей, join по составному ключу `(user_id, patch_id)` |

Полное имя класса: `com.vanmors.dataskew.<класс из таблицы>`.

## Генерация данных

Скрипт `DataGenerator.java` генерирует два синтетических набора данных:

| Таблица | Размер | Распределение | Поля |
|---|---|---|---|
| **users** | 1 000 000 записей | Равномерное | `user_id` (long), `name` (string) |
| **transactions** | 10 000 000 записей | Контролируемый перекос по `user_id` | `transaction_id` (long), `user_id` (long), `amount` (double) |

Параметры перекоса:
- **Горячий ключ:** `user_id = 42`
- **Доля горячего ключа:** 70% от всех транзакций (~7 000 000 строк)
- Остальные 30% (~3 000 000 строк) распределены равномерно по 999 999 пользователям

## Методология бенчмарка

Каждый бенчмарк:

1. Генерирует и кэширует данные (transactions + users)
2. Выполняет `transactions JOIN users ON user_id`:
   - Сначала обычным shuffle join (baseline)
   - Затем с применением исследуемого метода
3. Для каждого режима:
   - **1 warmup-прогон** (прогрев JVM, JIT-компиляция)
   - **3 замера** с усреднением результатов
4. Собирает метрики через `SparkListener`:
   - Время выполнения: avg / min / max (мс)
   - Объём shuffle read / write (avg)
   - Peak execution memory (макс. пиковая память)
   - Время самой медленной задачи (avg, мс)
   - Количество задач и стадий (avg)

## Структура проекта

```
src/main/java/com/vanmors/dataskew/
    Main.java                  — запуск всех бенчмарков последовательно
    DataGenerator.java         — генератор синтетических данных с перекосом
    BenchmarkUtils.java        — сбор метрик, warmup, усреднение, создание SparkSession
    AQE/                       — Adaptive Query Execution
    salting/                   — Salting
    broadcast/                 — Broadcast Join
    preaggregation/            — Pre-aggregation (map-side reduce)

    PRPQ/                      — Partial Redistribution & Partial Query

```

### Анализ результатов

#### 1. Broadcast Join — лидер по всем метрикам

**556 мс** (×6,2 от baseline), shuffle фактически нулевой (118 B — только координация broadcast), peak memory 30,5 MB. Таблица users (1M строк, ~23 MB) целиком рассылается каждому executor-у, и join выполняется локально без обмена данными.

**Ограничение:** применим только когда малая таблица помещается в память каждого executor-а. При росте users до десятков ГБ — неприменим.

#### 2. Co-partitioned (Map-side) Join

**1 170 мс** (×2,8 от baseline), shuffle = 11,5 KB. Обе таблицы заранее со-разбиты по `user_id` на 200 партиций и закэшированы. При join Spark не выполняет shuffle — данные уже в нужных партициях.

**Ограничение:** стоимость предварительного `repartition()` + `cache()` **не включена** в замер. В продуктовой среде этот метод реализуется через Hive bucketed tables, которые сохраняют разбиение между запусками.

#### 3. Pre-aggregation — эффективен, но меняет семантику

**1 835 мс** (×2,5 от baseline), shuffle снижен на 37% (20,4 → 12,9 MB), peak memory — в 4× (224 → 56 MB). Pre-aggregation группирует 10M транзакций в ~950K уникальных `user_id`.

**Важно:** результат содержит **950K строк** вместо 10M — это агрегаты (count, sum, avg), а не исходные транзакции. Подходит для аналитических задач, не для задач, где нужен каждый рекорд.

#### 4. AQE — неожиданная деградация на малом кластере

**3 659 мс** (×0,8 от baseline) — AQE оказался **медленнее** baseline. Это объясняется агрессивным coalesce: AQE сократил число задач с 209 до 15, объединив мелкие партиции. При 6 executor-cores (3 worker × 2 cores) это привело к 15 крупным задачам, которые не могут эффективно параллелиться — время самой медленной задачи выросло с 1 332 до 2 120 мс.

AQE coalesce оптимален для крупных кластеров, где сотни мелких задач создают overhead планировщика. На малом кластере укрупнение задач **ухудшает** параллелизм. Для данного масштаба данных (10M строк) и кластера (6 cores) AQE coalesce избыточен.

#### 5. Salting — overhead от репликации

**4 773 мс** (×0,7 от baseline). Salting размножает таблицу users в 10× (10M записей users × 10 salt buckets = 10M), что увеличивает shuffle в 4,7× (20,4 → 95,7 MB). На малом кластере overhead от дополнительного shuffle и объёма данных перевешивает выигрыш от распределения горячего ключа.

Peak memory при этом **снизилась** (224 → 66 MB) — горячий ключ действительно распределился по партициям. На кластере с десятками executor-ов и при бо́льшем объёме данных salting начнёт приносить выигрыш.

#### 6. PRPQ — overhead от множества стадий

**8 274 мс** (×0,4 от baseline). Алгоритм создаёт 11 стадий вместо 4: определение heavy hitters → разделение данных → broadcast join для горячих → shuffle join для лёгких → union. На 6 cores все эти дополнительные стадии выполняются последовательно, а их overhead (особенно дополнительные shuffle в 94 MB / 74 MB) не окупается.

При сетевом shuffle на 100+ узлах PRPQ будет эффективен: broadcast для 70% данных исключает основной трафик, а shuffle для оставшихся 30% — равномерный.

#### 7. Patch-based — максимальный overhead

**16 307 мс** (×0,2 от baseline). Самый сложный алгоритм: `row_number()` с window-функцией по 7M строк горячего ключа → детерминированное назначение patch_id → `explode()` для репликации users → join по составному ключу. 13 стадий, 1 220 задач, shuffle 180/162 MB, peak memory 504 MB.

Метод спроектирован для кластеров с десятками executor-ов, где overhead от подготовки амортизируется параллельным выполнением, а детерминированное разбиение на патчи даёт более предсказуемую балансировку, чем случайный salting.

## Ограничения данного анализа

### 1. Масштаб кластера

3 worker × 2 cores × 2 GB — это минимальный кластер. Методы Salting, PRPQ и Patch-based проектировались для кластеров с десятками-сотнями executor-ов. На 6 cores overhead от дополнительных стадий и shuffle не окупается параллелизмом.

**Что это меняет:**
- На 6 cores задачи конкурируют за ресурсы; на 60 cores дополнительные задачи выполняются параллельно
- Сетевой shuffle между 3 контейнерами в bridge-сети значительно быстрее, чем между физическими узлами в реальном кластере
- Эффект straggler-а при 3 worker-ах слабее, чем при 30 — один медленный executor из 3 блокирует 33% мощности, из 30 — только 3%

**Решение:** масштабировать до 10–30 worker-ов или использовать cloud-кластер (EMR, Dataproc).

### 2. Масштаб данных

10M строк — сравнительно небольшой объём для Spark. Overhead от координации задач (планировщик, сериализация, сетевые handshake) составляет значительную долю общего времени.

При миллиардах строк:
- Стоимость shuffle станет доминирующей — методы, избегающие shuffle (Broadcast, Co-partitioned), покажут ещё больший выигрыш
- Straggler-эффект станет критичным — один executor с 70% данных будет работать часами
- Методы Salting, PRPQ, Patch-based начнут окупать свой overhead

### 3. Модель перекоса

Текущая модель (один ключ = 70% данных) — крайний случай. В реальных данных:
- Несколько горячих ключей (Zipf/степенное распределение)
- Меньшая степень перекоса (5–20% на топ-ключи)
- Перекос может меняться во времени

PRPQ и Patch-based рассчитаны на множество горячих ключей — при одном ключе broadcast join для него тривиален. С Zipf-распределением эти алгоритмы покажут свои преимущества.

### 4. Co-partitioned Join: стоимость подготовки

Стоимость `repartition()` + `cache()` **не включена** в замер. Эта операция сама требует full shuffle обеих таблиц. Метод оправдан только при многократных join-ах по одному ключу.

Кроме того, без Hive Metastore невозможно использовать полноценные bucketed tables — текущая реализация через `repartition()` + кэш работает только в рамках одной SparkSession.

### 5. Pre-aggregation: несопоставимость результатов

Pre-aggregation возвращает **~950K строк** вместо 10M — это агрегированный результат, а не полный join. Прямое сравнение времени с baseline (10M строк) некорректно, т.к. задачи имеют разную семантику и разный объём результата.

### 6. AQE coalesce на малом кластере

AQE показал деградацию из-за агрессивного coalesce (209 → 15 задач). На малом кластере (6 cores) укрупнение задач снижает параллелизм. Это не баг AQE, а следствие масштаба: настройки AQE оптимизированы для кластеров с сотнями cores, где сотни мелких задач создают overhead планировщика.

Возможное решение: настроить `spark.sql.adaptive.advisoryPartitionSizeInBytes` и `spark.sql.adaptive.coalescePartitions.minPartitionSize` для конкретного кластера.
